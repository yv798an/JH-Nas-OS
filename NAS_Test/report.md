### 热盘（page cache 命中）

| 方案 | 云端 median | 云端 比值 | 板端 median | 板端 比值 |
|------|-----------:|:--------:|-----------:|:--------:|
| sync | 3931.1* | 1.00 | 1370.8 | 1.00 |
| QD=1 | 4563.8 | 1.16 | 1250.0 | 0.91 |
| QD=4 | 4390.8 | 1.12 | 1225.6 | 0.89 |
| QD=16 | 3955.7 | 1.01 | 1102.8 | 0.80 |
| QD=64 | 4149.7 | 1.06 | 881.6 | 0.64 |

\* 云端热 sync 受冷读污染，不可靠。

**结论（本报告最重要的一条）**
- **冷盘**：io_uring 在板端有正收益 **1.3–1.4×**；云端因虚拟盘同步已打满，几乎无收益。收益来自"异步提交"，QD 加深几乎不再涨。
- **热盘**：io_uring 在板端**反而更慢，且越深越慢**（QD64 只有 sync 的 64%）；云端略快但噪音大。原因：缓存命中时同步 `read()` 就是 memcpy，io_uring 额外付出 ring 建立/线程/缓冲交接/自旋的开销。
- 综上：**io_uring 的价值严格取决于数据是否在 page cache、以及设备是否被单流打满**，正是"要看负载"的实证。

### 6.1 看门狗复位循环（重要案例）
- **现象**：板子反复复位。
- **根因**：开机时 BusyBox `ifup` 未拉起网络接口，**`lo` 处于 DOWN** → 健康探活连 `127.0.0.1` 报 `No route to host` → watchdog 连续判不健康 → 复位 → 循环。
- **修复**：新增 `/etc/init.d/S30netup`，直接用 `ip` 命令保证 `lo`/`eth0` 开机即 up；停用原 `/etc/init.d/S40network`；并把看门狗超时从 `15s` 放宽到 `60s`（原 `test-timeout=15` 与 `watchdog-timeout=15` 相等，本就临界）。
- **验证**：重启后 `lo=127.0.0.1`、`eth0` 静态地址自动就位、`health=0`、连续 5 次探活全 0。

## 7. 板端现场分解（procfs + 用户态时间打点）

板端内核无 perf/PMU，改用两层现场证据：procfs 线程统计 +
`AsyncFileReader` 内的 `steady_clock` 打点。数据来自
`ab-handoff-yield-{sda1,sdb1}`。

### 7.1 冷/热读（yield，64 KiB，QD=8）

| 场景 | wall (s) | 读取 CPU/wall | 消费 CPU/wall | submit | handoff | queue |
|---|---:|---:|---:|---:|---:|---:|
| 冷读 sda1（USB 3.0） | 0.55 | 40.0% | 100.0% | 99.1% | 99.4% | 1.2% |
| 冷读 sdb1（USB 2.0） | 6.42 | 3.4% | 100.0% | 99.9% | 100.0% | 0.1% |
| 热读 sda1 | 0.12 | 100.0% | 100.0% | 97.3% | 97.8% | 7.7% |
| 热读 sdb1 | 0.12 | 100.0% | 100.0% | 97.3% | 97.8% | 7.8% |

- 冷读 sdb1 的 `handoff` 占满 wall，消费者 CPU 6.42 s = wall——全程忙等。
- 冷读 sda1 同样约 99% 自旋，但 wall 只有 0.55 s；按 GiB 归一化后为
  3.2 vs 53 cpu-s/GiB，差异来自 wall 长度而非自旋比例。
- 队列驻留仅 0.1–7.8%，开销不在排队。

### 7.2 HTTP t8（procfs）

| 服务端 | 盘 | `nas-http` CPU 占比 | vcsw | nivcsw |
|---|---|---:|---:|---:|
| sync | sda1 | 99.9% | 11117 | 150 |
| sync | sdb1 | 99.8% | 13289 | 102 |
| uring | sda1 | 99.8% | 12130 | 68549 |
| uring | sdb1 | 99.8% | 12297 | 58711 |

- uring 的非自愿上下文切换约为 sync 的 **450–575 倍**；`nas-http` 占捕获到的
  持久线程 CPU 的 99.8%。
- 读取线程短命（每请求创建/销毁），未能在前后快照中稳定捕获；io_bench 中其
  CPU 仅 0.22 s，远小于消费者。

### 7.3 Handoff A/B（yield vs condvar）

- **sdb1 冷读**：CPU 53.1 → 5.2 cpu-s/GiB（−90%），吞吐 19.9 → 19.0 MiB/s
  （−5%），净收益。
- **sda1 冷读**：CPU 6.16 → 3.37（−45%），但吞吐 231.8 → 174.0（**−25%**）；
  原因是快盘上缓冲池耗尽时的 1 ms 超时退避打断了流水线。
- **HTTP t8**：uring 吞吐 267 → 354 MiB/s（**+33%**），服务端 CPU
  49.7% → 66.4%，仍低于 sync 的约 108%。
- 结论：blocking handoff 在慢盘/HTTP 是净收益，快盘冷读需配合 buffer-release
  通知或保留 yield。

## 8. 结论

1. **io_uring 的收益取决于"冷/热 + 设备是否打满"**：yield 版板冷盘 1.3–1.4×，板热盘 0.64–0.91×（更慢），云冷盘 ~1.0×。
2. **yield 版经 HTTP 时 io_uring 更慢**，跨平台一致 → 支持"可配置 + 回退、非默认全开"。
3. 板端现场分解（procfs + 时间打点）把开销定位到消费者交接等待：冷读 handoff 占 wall 99–100%；HTTP t8 uring 的非自愿切换为 sync 的 450–575 倍（§7）。
4. 条件变量 A/B 是负载相关权衡：慢盘冷读 CPU −90%、吞吐持平；快盘冷读吞吐 −25%；HTTP uring 吞吐 +33%（§7.3）。
4. **⚠️ README 的 "sync 953 / io_uring 2698（约 2.8×）" 在本次全部测量中均未复现**：板冷 171→235、板热 1371→882、云冷 143→144、云热 3931→4564，没有一组接近。发帖前**不要引用 README 那组数字**，改用本报告实测值；若要保留原表，须注明其测试条件或重新复现。

### 10.5 结论与数据充分性

**结论（现有数据可直接支撑）**
1. **冷盘快设备**（sda1，USB 3.0）：io_uring 吞吐 1.3–1.4×，但 CPU-s/GiB 约 2×；
2. **冷盘慢设备**（sdb1，USB 2.0）：设备已打满，io_uring 仅 1.05×、CPU 约 11×，
   加深 QD 无收益；
3. **热盘**（两块盘一致）：io_uring 全面更慢（0.63–0.93×），QD 越深越慢；
4. **HTTP**：io_uring 更慢，并发越高差距越大（t4/t8 为 0.63–0.69）；CPU 受限、
   与存储无关；
5. 机制解释用 §7：消费者 `handoff_wait` 占 wall 99–100%，HTTP t8 uring 的
   `nivcsw` 为 sync 的 450–575 倍；条件变量 A/B 见 §7.3。
   → 总结论：**io_uring 只在“冷数据 + 设备未被单流打满”时值得开，且要配
   CPU 预算；交接方式按负载选：慢盘/HTTP 用 condvar，冷快盘保留 yield
   或先实现 buffer-release 通知。**

**仍然不够（需要另做）**
1. 板端硬件计数器（cycles/instructions/IPC）：内核未开 `CONFIG_PERF_EVENTS`；
2. 消除 condvar 在快盘冷读的 25% 吞吐损失：用 `BufferPool::release` 回调
   `notify` 生产者，替代当前 1 ms 超时退避；
3. 云端当前代码复测：非必需，除非要引用云端绝对值或做同版本跨平台对比。

**判定：核心论点和两台存储的行为都已够用；不补硬件计数器也不影响结论。**
